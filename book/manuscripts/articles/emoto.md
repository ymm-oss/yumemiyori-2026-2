# 執筆に専念するための技術同人誌テンプレートの設計

技術同人誌を製作するとき、「本文を書く」以外の作業負担が大きいです。本の製作は執筆だけではありません。組版の調整、目次や奥付の生成など、いくつもの工程があります。さらに、本誌のような複数の執筆者がいる場合は、それぞれの記事の管理や調整もあります。これらも本文の執筆と同じくらい大切な作業ですが、本文の執筆に比べると、つい後回しにしがちです。

本誌の製作では、そうした作業をできるだけ自動化しています。執筆者は自身の記事を書くだけです。技術同人誌を製作する過程で起こる「非執筆コスト」を削減するように、製作プロジェクトを設計しています。

本誌の製作プロジェクトは執筆テンプレートとして、公開しています。本記事では、そのテンプレートの目的、どのような仕組みで自動化しているのかを、実際のファイル構成と処理の流れにそって説明します。手作業の編集作業が必要になる部分も含めて、どこまで自動化できて、どこからが人手が必要なのかを整理していきます。

## 執筆テンプレートの製作

技術同人誌は、Web ブラウザで読むブログ記事や社内ドキュメントと違い、体裁を整えた紙の書籍として完成させる必要があります。たとえば、次のような作業が発生します。

- 組版（レイアウト）をどうするか
- 記事をどう管理するか
- 目次や奥付など、記事以外のに項目をどう管理するか
- 表紙画像や PDF の出力設定をどうするか

これらは「本文を書く」とは別の作業ですが、最終的に書籍自体の品質に直結します。しかし、目次や組版などの作業負荷が積み重なると、本来注力すべき執筆が疎かになりえます。そこで、執筆者が本文に集中できるようにと、執筆テンプレートを製作しました。

そのテンプレートは 2023 年ごろに、本の組版や製作を自動でおこなう仕組みとして公開しました。本誌もこのテンプレートを使って作成してきました。GitHub で管理し、記事の追加や構成の変更は PR ベースで行えるようにしています。

一方で、本誌のような複数人で製作する場合、１つの記事管理ファイルが同時に編集されるという問題ありました。特に締切間近で記事追加の PR が一斉に上がったときは、コンフリクトが毎回発生するため、またか...と頭を悩ませていました。

そこで、今年の夏に、記事管理を大きく見直しました。記事管理の自動化を改善し、執筆者が本文に集中しやすい環境を整えました。記事の管理・目次・著者紹介・奥付の生成をより一貫した仕組みに整理しました。

## 執筆テンプレートの大まかな流れ

執筆テンプレートは、主に組版や体裁をサポートするテンプレートとしてリリースしました。以前の制作過程は、大まかに次のようになっていました。

1. 執筆者が Markdown で記事を書く
1. 執筆者の紹介ページを作成する
1. 執筆者または編集者が config ファイルに、記事ファイルを書き込む
1. 編集者が config ファイルで掲載順を精査する
1. 編集者が記事タイトルと著者名を並べた目次ページを作成する
1. 編集者が奥付けを更新する

嬉しいことに本誌は多くの方が参加されます。そのため、記事追加の PR で config ファイルが毎回コンフリクトしていました。また、記事ファイルが多いので記事掲載や目次などで漏れがないか、確認していました。ここ最近の製作では、Claude Code などの AI に目次や紹介ページを作成させて負荷軽減してますが、それでも目視確認は必要です。

今回行った大規模な改修では、これまでの手動作業を自動化しました。新しい執筆テンプレートの流れは次のようになりました。

1. 執筆者が Markdown で記事を書く
2. 執筆者がその Markdown のメタデータにタイトル・著者・プロフィールを記述する
3. 編集者が本の構成と目次の順番を YAML で定義する
4. 編集者が自動生成スクリプトを実行して、目次・著者紹介・奥付を自動生成する
5. 編集者が任意で手動調整して、PDF を出力する

執筆者は記事本文に加えて、タイトル・著者・プロフィールなどのメタデータも記述します。その情報をもとに、目次・著者紹介・奥付が自動生成されます。記事追加の PR でコンフリクトに悩まされることはなくなりました。

編集者は YAML に記述するのは、基本的に掲載順と奥付の内容だけです。スクリプトで生成するため、AI に生成を任せた場合に起きる誤りを避けられます。また、自動化だけで仕上げきれない箇所も、最終段階で手動調整できます。こうして編集作業の時間を減らし、執筆により多くの時間を使えるようにしています。

なお、表示画像の作成自動化はいまだに未対応です。今は生成 AI で自動生成させることもできますが、本誌は社内のデザイナーさんに依頼してます。毎回かっこいい表紙を仕上げてもらっています、いつもありがとうございます！

## テンプレートの全体像

新しい執筆テンプレートでは、記事や設定ファイル、自動生成したページなどを、用途に応じて別々のディレクトリで管理しています。主なファイル構成は次のとおりです。

```text
book/
└─ manuscripts/
   ├─ articles/
   │  ├─ 執筆者Aの記事.md
   │  :
   │  └─ 執筆者Zの記事.md
   ├─ config/
   │  ├─ articles.yml
   │  ├─ entry.yml
   │  └─ generate.yml
   ├─ generated/
   ├─ edited/
   ├─ pages/
   └─ vivliostyle.config.js
```

各ディレクトリで管理する内容を、表にまとめました。

| ディレクトリ | 役割 |
|:--|:--|
| articles/ | 執筆者が書く記事マークダウンを格納する |
| config/ | 編集者が本の掲載順や奥付け、目次の見た目などのルールを定義する |
| generated/ | 自動生成される目次・著者紹介・奥付を格納する |
| edited/ | 手動で微調整するための編集用コピーを格納する |
| pages/ | はじめにやあとがきなどの固定ページを格納する |

執筆者が主に触れるディレクトリは articles/ で、ここに記事の Markdown ファイルを格納します。テンプレート側が自動で取り込み、本を製作します。

編集者が管理するディレクトリは config/ で、掲載順や奥付けを定義します。

| 設定ファイル | 役割 |
|:--|:--|
| <span class="nowrap">articles.yml</span> | 記事の順番を制御する。ファイルがない場合は、articles/ 配下の Markdown ファイルをファイル名順で自動的に並べる。 |
| entry.yml | 本全体の構成順を定義する。目次や固定ページ、記事一覧の配置順などを決める。 |
| <span class="nowrap">generate.yml</span>  | 著者紹介や奥付のテンプレートを定義する。本文の内容ではなく、書籍としての見せ方を決める。 |

本のタイトルや著者名などの書籍情報は vivliostyle.config.js で定義します。今 YAML で定義する内容、vivliostyle.config.js で定義する内容があって、データ定義の責務が曖昧なので改修したいですね。今回の改修で完全に見落としてた。

このテンプレートでは、執筆者は「どこに何を書けばいいか」を知っていれば十分です。執筆の本質は本文そのものに集中し、構成や体裁、目次や奥付の整合はテンプレート側が担います。

編集者が YAML を調整するだけで、製作工程の多くを自動化できる、というのがこのテンプレートの大きな特徴です。

## 文章のメタデータから本全体を組み立てる

新しいテンプレートでは、記事のメタデータ（Front Matter）を読み取り、目次や著者紹介に反映します。各記事には、たとえば次のようにメタデータを記述します。

```markdown
---
class: content
title: 執筆に専念するための技術同人誌テンプレートの設計
author: 江本光晴
profile: |
  日頃は iOS アプリの開発をやっています。
---
```

ここの title、author そして profile のメタデータが、後段の自動生成に利用されます。目次では記事タイトルが自動で拾われます。著者紹介ページでは著者ごとのプロフィールがまとめられます。奥付には本のタイトルや版情報が反映されます。

この設計の利点は、本文のときと同じ情報が、別の場所で重複管理されないことです。以前は、目次タイトルや著者紹介文を手作業でまとめていました。見出しや著者情報が変わるたびに、別ファイルを更新しなければならず、編集作業が増えていました。

今回のテンプレートでは、各記事の情報を一か所に書いておくと、その情報が必要な場所に自動で流れます。執筆者がタイトルを変えると目次が変わる。著者名を変えると著者紹介が変わる。プロフィール文を更新すると、著者紹介ページにも反映される。こうして、書籍全体の整合性が自動的に保たれます。

## 自動生成されるページ

このテンプレートでは、執筆者が直接編集するのは記事の Markdown ファイルです。目次・著者紹介・奥付といったページは、書誌情報と記事のメタ情報から自動生成されます。生成されたファイルは generated/ にそれぞれ配置されます。

### 目次

entry.yml で定義した記事一覧や奥付けなどを掲載順から、ひとつの目次を生成します。記事一覧は、articles.yml で定義した掲載順を元に、記事タイトルと名前から生成します。

これにより、記事ファイルを追加しただけで、目次が再生成されます。手作業で index.md を更新する必要はありません。

### 著者紹介

各記事の著者名とプロフィールを集約して、著者ごとの紹介ページを作ります。同じ著者が複数の記事を書いていた場合でも、自動的にタイトルを１つにまとめます。

プロフィールの書式も generate.yml で調整できます。profile_template は次のような形式です。

```yaml
profile_template: |
  ### {author}（{title}）

  {profile}
```

ここにある {author} や {title} は、書籍中の各著者プロフィールを整えるためのテンプレート変数です。テンプレートを変えるだけで、著者紹介の見た目を切り替えられます。

### 奥付

書籍のタイトル、発行者、版履歴、連絡先などをまとめて生成します。たとえば generate.yml に次のように定義します。

```yaml
edition_history: 初版

colophon_rows:
  - label: 発行
    value: ゆめみより製作委員会
  - label: 連絡先
    value: https://x.com/yumemiinc
```

## 編集作業を分離する

前節で挙げた目次や奥付などは自動生成できますが、最終的な本の体裁に合わせて微調整したい場合もあります。そこで、このテンプレートでは、自動生成するファイルと手動編集するファイルを別のディレクトリで管理しています。

自動生成されたファイルは generated/ ディレクトリに出力されます。生成結果を手動で編集したい場合は、コマンド　yarn edit を実行して edited/ ディレクトリにコピーします。編集者は edited/ ディレクトリにコピーされたファイルを修正します。

PDF をビルドするときは、edited/ ディレクトリにファイルがあればそちらを優先し、なければ generated/ ディレクトリのファイルを使います。

| ディレクトリ | 役割 |
|:--|:--|
| generated/ | スクリプトが毎回生成するファイルを置く |
| edited/ | 自動生成されたファイルを手動で調整したものを置く |

コマンドは、まず generated/ のファイルが更新され、その後に edited/ にまだないファイルだけがコピーされます。すでに edited/ にあるファイルは上書きされないため、編集者が加えた調整は保護されます。

edited/ にコピー済みのファイルは、記事のタイトルや著者情報を変更しても自動では反映されません。更新したい場合は、generated/ の内容を確認しながら該当する edited/ のファイルを自分で編集する。もしくは、既存の編集内容を退避して edited/ から削除したうえでコマンドを再実行し、必要な調整を加え直します。

## 本の順番とページ構成も設定ファイルで管理する

本全体の構成は、config ディレクトリにある entry.yml で管理します。ここには、目次、本文、著者紹介や奥付などを、本誌に配置する順番で記述します。

たとえば、次のように定義します。この例では、生成した目次ページの次に「はじめに」の固定ページを置きます。その後に記事一覧を並べ、最後に著者紹介と奥付を配置しています。目次ページ自身、著者紹介や奥付は目次ページに表示しないためので toc: false としています。

```yaml
- type: generated
  id: index
  toc: false

- type: page
  title: はじめに
  file: pages/preface.md
  toc: true

- type: articles
  toc: true

- type: generated
  id: authors
  toc: false

- type: generated
  id: colophon
  toc: false
```

entry.yml の各項目には、配置するページの種類と、目次に表示するかどうかを指定します。

| 項目 | 内容 | 備考 |
|:--|:--|:--|
| <span class="nowrap">type</span> | 配置するページの種類 | generated、page、articles のいずれかを指定する |
| id | 自動生成ページの種類 | generated の場合に index、authors、colophon のいずれかを指定する |
| <span class="nowrap">title</span> | 固定ページや自動生成ページの見出し | page の場合は必須 |
| file | 固定ページの Markdown ファイル | page の場合に指定する |
| toc | そのページを目次に表示するかどうか | true なら表示し、false なら表示しない |

type には、次の３種類があります。

| type | 役割 | 指定する項目 |
|:--|:--|:--|
| <span class="nowrap">generated</span> | スクリプトが生成するページを配置する。 | id で目次、著者紹介、奥付を選ぶ。 |
| <span class="nowrap">page</span> | pages ディレクトリなどに用意した固定ページを配置する。 | title と file を指定する。 |
| <span class="nowrap">articles</span> | articles ディレクトリの記事をまとめて配置する。 | 記事の順番は articles.yml の設定に従い、設定がなければファイル名順になる。 |

こうして本の構造を明示しておくことで、執筆者は「どのファイルをどこに置くか」を意識しなくてよくなります。構成の責務が自動化のレイヤーに移るからです。

## ビルドを簡単にし、出力を再現可能にする

本文を書き終えたら、コマンドを実行して PDF を作成します。ビルドの前に自動生成スクリプトが実行されるため、記事の追加やタイトルの変更も、目次や著者紹介に反映されます。

電子版 PDF を作成する場合は、次のコマンドを実行します。このコマンドは、目次・著者紹介・奥付を生成したあと、Vivliostyle で本全体を組版し、電子版 PDF を出力します。記事を追加するたびに目次を手作業で更新する必要はありません。

```shell
yarn build
```

印刷入稿用の PDF を作成する場合は、次のコマンドを実行します。電子版と印刷入稿用では必要な設定が異なるため、用途に応じてビルド方法を分けています。同じ原稿からそれぞれの PDF を生成できるので、版ごとに手作業で構成を作り直す必要がありません。

```shell
yarn build:press
```

表紙画像を電子版 PDF に追加する場合は、表紙画像を book/cover/cover.png に置いたうえで、次のコマンドを実行します。

```shell
yarn cover
```

これにより、表紙画像を結合した PDF が book/output/ebook_covered.pdf として作成されます。ただし、表紙画像の品質や PDF の仕上がりは最終的に確認が必要です。問題がある場合は、PDF 編集ソフトなどで手動結合してください。

このように、原稿から各種 PDF を作る工程をコマンドとして定義することで、特定の担当者だけが知っている手順を減らせます。必要な設定と依存ツールがそろっていれば、誰が実行しても同じ手順で本を出力できます。

なお、この執筆テンプレートのパッケージ管理は、私の好みで yarn v4 を採用しています。Node.js から corepack の同梱が廃止されたので、このまま v6 にするか、別のパッケージマネージャーの移行するか、どうしようかと考えています。

### Makefile を使って Docker 上でビルドする

Node.js や Yarn をローカル環境にインストールしたくない場合は、Makefile のコマンドが利用できます。ホスト側の Node.js や Yarn のバージョンに依存せず、プロジェクトで指定したイメージを使ってビルドできます。

電子版 PDF を生成して開く場合は、make run を実行します。

```shell
make run
```

PDF の生成だけを行う場合は make pdf、印刷入稿用 PDF を生成する場合は make pdf_press を使います。表紙画像を電子版 PDF に結合する場合は、make cover を実行します。

```shell
make pdf
make pdf_press
make cover
```

Makefile の処理で利用した依存関係は、ローカルの Node.js や Yarn のグローバル環境に影響しません。生成物やコンテナ関連のファイルを削除する場合は make clean を使えます。

## GitHub Actions で PR とリリースを自動化する

ローカルでビルドするだけでなく、GitHub Actions も利用できます。GitHub 上で原稿を PR にすると、CI として PDF を自動生成し、PR から確認できるようにしています。また、リリース作業も対応しています。

### PR で PDF を確認する

PR が作成されたとき、または PR の内容が更新されたときは、電子版 PDF が自動的に生成されます。生成された PDF は Actions のアーティファクトとしてアップロードされ、PR に PDF へのリンクがコメントされます。

このリンクから PDF をダウンロードすれば、記事の追加や修正が本全体の組版にどう反映されたかを、簡単に確認できます。目次や著者紹介などの自動生成ページも含めて確認できるため、文章のレビューと同時に書籍全体の仕上がりをレビューできます。

### タグで PDF をリリースする

発行時には、版を表すタグを GitHub にプッシュします。初版や初版二刷のように、タグの末尾を「版」または「版」と「刷」の組み合わせにします。

```text
初版
初版2刷
第二版一刷
```

この形式のタグをプッシュすると、GitHub Actions が電子版 PDF と印刷入稿用 PDF を生成し、それらを添付した GitHub Release を作成します。表紙画像や PSD ファイルが cover ディレクトリにあれば、それらもリリースのアセットとして追加されます。

タグを起点に PDF の生成とリリース作成までを自動化できるため、発行時に同じ手順を手作業で繰り返す必要がありません。一方で、電子版 PDF への表紙画像の結合や、リリース後のアセット確認など、最終的な確認は人が行います。

## 自動化してない部分はどこか

ここまで説明してきた仕組みによって、記事の管理、目次や著者紹介の生成、PDF の出力は自動化できます。一方で、文章やデザインの良し悪しを判断する作業まで自動化していません。生成 AI などを導入すれば、文章の書き方や質を改善できるでしょう。

本誌は技術同人誌です。執筆者それぞれが表現を制限されず、好きなように書けることを大切にしているため、文章の改善を目的とした生成 AI は導入していません。ただし、最低限の textlint ツールは導入しています。しかし、実際にそれを利用するかは、執筆者しだいです。

書籍としての最終的な品質は、執筆者と編集者が PDF を確認し、必要な修正を加えながら仕上げます。自動化によって定型的な作業を減らし、人が内容と仕上がりを確認する時間を確保する、という役割分担です。

| 作業 | 自動化できる部分 | 人が担当する部分 |
|:--|:--|:--|
| <span class="nowrap">表紙</span> | 表紙画像を PDF に結合する | デザインやイラストを考え、完成した画像を用意する |
| <span class="nowrap">目次・奥付</span> | 記事情報や設定からページを生成する | 表現や掲載内容を確認し、必要に応じて修正する |
| <span class="nowrap">記事の構成</span> | 記事を設定した順番で配置する | 記事同士のつながりや全体の分量を確認する |
| <span class="nowrap">文章</span> | textlint で表記ゆれや誤りの候補を検出する | 内容の正確さ、読みやすさ、文体を確認する |
| <span class="nowrap">PDF</span> | 電子版や印刷入稿用の PDF を生成する | ページの崩れ、画像、リンク、印刷仕様を確認する |

## まとめ

技術同人誌を作るには、本文を書くことに加えて、記事の管理、目次や著者紹介の作成、奥付の準備、組版、PDF の確認など、多くの作業が必要です。執筆者がこれらを個別に管理すると、本文を書く時間や意欲が削られてしまいます。

このプロジェクトは、そうした負担を減らす目的で 2023 年ごろに公開しました。当初から本の組版や体裁を自動化し、今年の夏には、複数人で記事を管理するときに起きていたコンフリクトを減らすため、記事のメタ情報から目次・著者紹介・奥付を生成する仕組みへ改修しました。

執筆者は articles ディレクトリに Markdown を追加し、記事のタイトルや著者情報を Front Matter に記述します。製作側は設定ファイルで本の構成や表示方法を定義します。その情報をもとに、ローカルのコマンドや Makefile、GitHub Actions が PDF の生成とリリース作業を支援します。

一方で、表紙のデザイン、記事の内容や文体、全体の構成、PDF の最終確認などは人が担当します。生成 AI を含めた自動化をすべての工程に適用するのではなく、執筆者が自由に表現できることと、編集者が品質を判断できることを大切にしています。

このテンプレートの目的は、人の作業をなくすことではありません。決められたルールに従う定型的な作業を自動化し、執筆者が本文に集中できる時間と、編集者が本全体を確認する時間を作ることです。技術同人誌を作るためのプロジェクト自身をコードで整備することで、書くことと本に仕上げることの両方を無理なく続けられるようにしています。
